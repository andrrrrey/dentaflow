# DentaFlow — описание проекта и архитектуры

> Документ написан простым языком для тех, кто хочет понять, **что это за система, из чего она состоит и почему она устроена именно так**. Подходит и разработчику, который только пришёл в проект, и руководителю, который хочет понять «как это работает под капотом».

---

## 1. Что это за продукт и зачем он нужен

**DentaFlow** — это интеллектуальный веб-дашборд для управления стоматологической клиникой.

Ключевая идея: клиника уже работает в медицинской информационной системе (МИС) **1Denta**. DentaFlow **не заменяет** её, а надстраивается сверху и добавляет то, чего в МИС нет:

- единый коммерческий и управленческий слой (CRM, аналитика, маркетинг);
- ИИ-подсказки администраторам и руководителю;
- единый центр всех коммуникаций с пациентами;
- автоматические задачи и напоминания;
- **исходящий ИИ-обзвон** базы пациентов голосовым роботом;
- **бонусную программу** для пациентов и **мотивацию персонала** (баллы/рейтинг).

Проще говоря: **1Denta — это «бухгалтерия» приёмов и медкарт, а DentaFlow — это «мозг продаж и управления» поверх неё.**

### Масштаб и контекст
- 1 клиника, до ~10 сотрудников.
- База ~17 000 пациентов (важная цифра — она объясняет многие технические решения, см. ниже).
- Клиника физически находится в Улан-Удэ (часовой пояс Москва +5) — это влияет на расписание фоновых задач.
- Деплой на VPS (Ubuntu) в облаке Timeweb.

### Из чего состоит продукт (модули)
1. **Дашборд руководителя** — ИИ-аналитика, воронка пациентов, загрузка врачей, рейтинг администраторов, ежедневный отчёт в Telegram.
2. **Центр коммуникаций + CRM-воронка** — единая лента входящих (Telegram, Max, ВКонтакте, сайт, телефония Novofon/Ростелеком), канбан-воронка сделок, карточка пациента «360°», ИИ-подсказки. Живые счётчики непрочитанного, колокольчик уведомлений и браузерные пуши.
3. **ИИ-обзвон (`aicallrobot` + Asterisk)** — голосовой робот сам звонит пациентам из выбранного сегмента, приглашает на осмотр и фиксирует исход. Отдельный подпроект (см. §5.9 и `aicallrobot/ARCHITECTURE.md`).
4. **Боты для пациентов (Telegram + Max)** — запись на приём, ИИ-ответы на вопросы, напоминания, бонусный баланс. Общая логика диалога для обоих каналов.
5. **Бонусная программа** — баллы пациентам, реферальные коды, сбор и модерация отзывов, подарочные сертификаты/скидки.
6. **Мотивация персонала** — баллы администраторам за действия (звонки, подтверждения, закрытие задач) и лидерборд.
7. **Дополнительные разделы**, выросшие со временем: маркетинг, сегменты базы пациентов, контроль качества звонков и скриптов, задачи, справочники, настройки интеграций (админка).

| Фронтенд | React 18 + TypeScript + Vite | Стандарт для интерактивных SPA; TypeScript ловит ошибки на этапе написания кода; Vite даёт быструю сборку и горячую перезагрузку. |

| Состояние клиента | Zustand | Лёгкий стор для авторизации, UI, коммуникаций и уведомлений — проще, чем Redux. |
| Графики / DnD / тосты | Recharts, @dnd-kit, react-hot-toast | Диаграммы дашборда, перетаскивание карточек в канбане, всплывающие уведомления. |

| Фоновые задачи | Celery (несколько worker + beat) | Тяжёлые и периодические операции вынесены из веб-процесса. |
| Боты | aiogram 3 (Telegram) + Max API + VK Callback API | Один слой бизнес-логики диалога на Telegram/Max; ВКонтакте подключён как канал приёма сообщений (ручной чат). |
| ИИ (аналитика/CRM) | OpenAI (GPT-4o / gpt-4o-mini) | Аналитика, подсказки, классификация пациентов и обращений. |
| ИИ-обзвон (голос) | Yandex SpeechKit + YandexGPT (в `aicallrobot`); TTS также fish.audio (S2.1 Pro) | Российское облако, хорошая русская речь; fish.audio — альтернативный синтез речи с меньшей задержкой ответа, выбирается на уровне кампании. |
| Телефония | Novofon **или** Ростелеком «Виртуальная АТС» (переключатель провайдера); Asterisk (PJSIP + AudioSocket + AMI) для обзвона | Оба провайдера дают историю звонков, записи и вебхуки через единый контракт; Asterisk инициирует исходящие звонки ИИ-обзвона и стримит аудио в робота. |
| Прокси / SSL | Nginx | Раздача статики фронтенда, SSL, проксирование на API и `/static`. |
| Упаковка | Docker + docker-compose | Одинаковое окружение локально и на проде, простой деплой. |

**Общий принцип выбора:** проверенные, асинхронные инструменты, которые хорошо работают вместе и не требуют большой команды для поддержки. Там, где нужна тяжёлая ML-функциональность (речь, GPT), — используются готовые облачные сервисы, а не своя инфраструктура.

### Почему именно такое разделение
- **Фронт и бэк разделены** (SPA + REST). Это позволяет независимо развивать интерфейс и логику, а также легко открыть API для будущих интеграций.
- **Тяжёлая работа — в Celery, а не в вебе.** Веб-процесс обязан отвечать пользователю быстро. Синхронизация с 1Denta или ИИ-анализ 17 000 пациентов не должны «вешать» интерфейс — поэтому они вынесены в фоновые задачи и, более того, в **разные очереди с разными воркерами** (см. §5.2).
- **Redis — универсальный «клей».** Одновременно служит брокером задач Celery, кэшем, хранилищем состояния диалогов ботов (по ключу с TTL) и шиной событий для real-time обновлений в браузере.
- **Telegram-бот — отдельный процесс.** Он держит long-polling/webhook и не должен зависеть от перезапусков веб-воркеров.
- **ИИ-обзвон изолирован в отдельный сервис (`aicallrobot`).** Голосовой контур (речь ↔ текст ↔ GPT в реальном времени) — самостоятельная система с собственным стеком (Yandex) и жизненным циклом; бэкенд DentaFlow оркеструет кампании, а телефонию берёт на себя Asterisk.

```
services/    — бизнес-логика и интеграции: one_denta (+ webhook), novofon,
               rostelecom, vk, ai_service, ai_calling_service, asterisk_ami,
               telegram_bot, bot_flow, max_vk, segments_service,
```

**Принцип слоистости** (важное архитектурное решение):
- **routers** — только приём запроса, проверка прав, вызов сервиса, возврат ответа. Тонкий слой.
- **services** — вся «умная» логика и общение с внешним миром.
- **models/schemas** — данные и их валидация.

Зачем так: логику можно переиспользовать и из роутера, и из Celery-задачи, и из бота, и тестировать отдельно. Роутеры остаются простыми и читаемыми.


Маршрутизация — `react-router-dom`. Каждая страница обёрнута в `ProtectedRoute` (проверка авторизации) и `AppLayout` (общий каркас с навигацией и колокольчиком уведомлений). ## 5. Ключевые механизмы и почему они так сделаны

### 5.1. Интеграция с 1Denta — «источник правды» о приёмах

1Denta — внешняя МИС с REST API (SQNS CRM Exchange). DentaFlow забирает оттуда пациентов, расписание, приёмы, справочники врачей и услуг.

Технические решения и их причины:
- **JWT-токен кэшируется в памяти процесса и автоматически обновляется при 401.** Не дёргаем авторизацию на каждый запрос — экономим время и нагрузку.
- **«Сырые» данные из 1Denta хранятся в поле `raw_1denta_data` (JSONB).** Если завтра понадобится поле, которое сегодня не разобрали, его не нужно тянуть из 1Denta заново — оно уже лежит в базе.
- **Синхронизация укрупнена в один часовой прогон.** Раньше был отдельный синк ближайших приёмов каждые 5 минут и справочников раз в час. Такая частота на ~8 процессах упиралась в **троттлинг авторизации 1Denta (HTTP 423 «account temporarily blocked»)**, поэтому теперь один комбинированный вход в час тянет справочники + пациентов + ближайшие приёмы, а полный тяжёлый прогон делается ночью (см. расписание).

### 5.2. Фоновые задачи Celery и расписание (beat)

Все периодические операции вынесены в Celery. Расписание (часовой пояс — Москва):

| Задача | Частота | Зачем |
|--------|---------|-------|
| Комбинированный синк (справочники + пациенты + ближайшие приёмы) | раз в час | Расписание и база актуальны, но без троттлинга 1Denta. |
| Полная синхронизация (1Denta + Novofon, все разделы) | ночью 02:30 | Тяжёлая — делается до генерации задач и когда никто не работает. |
| Проверка «зависших» лидов | каждые 5 мин | Не упустить пациента, с которым давно не связывались. |
| Обновление ИИ-инсайтов | раз в час | Аналитика на дашборде свежая. |
| Ежедневный отчёт в Telegram | 20:00 | Итоги дня руководителю. |
| Напоминания о приёме | каждые 15 мин | Своевременные сообщения пациентам. |
| Диспетчер ИИ-обзвона (окна/слоты кампаний) | каждую минуту | Вовремя запускать звонки в разрешённые окна. |
| Создание задач на обзвон (подтверждение завтрашних приёмов) | 03:00 МСК = 08:00 в Улан-Удэ | Задачи готовы ровно к открытию клиники — у админа весь день на обзвон. |
| Создание задач-follow-up по вчерашним | 03:05 МСК | Догнать тех, кто был вчера. |
| Деактивация просроченных задач | 00:05 | Чистка перед генерацией новых. |

**Очень важное решение — разделение очередей Celery на несколько отдельных воркеров:**
- `celery_worker` слушает `default,sync` (concurrency=4) — обычные задачи и синхронизация;
- `celery_worker_segments` слушает `segments` (concurrency=1) — тяжёлый пересчёт сегментов базы. Причина прямо описана в коде: иначе ночная полная синхронизация и синки «съедали» единственный воркер, и пересчёт сегментов навсегда зависал в статусе «в очереди»;
- `celery_worker_ai` слушает `ai` (высокая concurrency) — ИИ-обзвон, где каждый активный звонок держит слот воркера на всё время разговора.

Изоляция гарантирует, что эти процессы не мешают друг другу.

### 5.3. Сегменты базы пациентов и ИИ — самый «хитрый» модуль

Это сохранённые умные списки пациентов, например: «незавершённое лечение», «несостоявшиеся консультации», «пора на гигиену». Часть из них формируется не простым SQL-фильтром, а **ИИ-вердиктом по истории визитов каждого пациента**.

Проблема: пациентов ~17 000. Прогонять всех через GPT каждый раз — дорого и медленно. Решения:
- **Кэш результата по «отпечатку» (fingerprint).** Для каждого пациента считается хэш его истории. Если история не изменилась — повторного обращения к OpenAI не происходит, берётся сохранённый результат. (Поля `ai_analysis_fingerprint`, `treatment_ai_fingerprint` в модели пациента; сами вердикты — в JSONB `ai_analysis` / `treatment_ai`.)
- **Более дешёвая модель и параллелизм для массового анализа** (`gpt-4o-mini`, до 15 параллельных запросов) — отдельно от точечного анализа, где используется `gpt-4o`.
- **Результаты участников сегмента сохраняются в БД** (`patient_segment_members`), чтобы при открытии списка не пересчитывать заново.
- Логика списков «привязана к реальным фактам визитов», а не к «рыхлым» ИИ-флагам — чтобы не попадать в список ошибочно.

Сегменты — ещё и «топливо» для ИИ-обзвона: кампания собирает свою аудиторию из выбранного сегмента.

### 5.4. ИИ-сервис с режимом «моков»

`ai_service.py` умеет работать **без ключа OpenAI**: в режиме разработки методы возвращают реалистичные данные на русском. Это позволяет показывать и разрабатывать дашборд, не тратя деньги на API и не требуя ключа. Также есть аккуратная обработка ошибки «закончилась квота/баланс» (`OpenAIQuotaError`) — чтобы система не падала, а корректно сообщала о проблеме.

### 5.5. Реал-тайм: WebSocket + Redis Pub/Sub, счётчики, колокольчик и браузерные пуши

Когда приходит новое сообщение от пациента, меняется сделка или создаётся уведомление, интерфейс обновляется без перезагрузки. Механизм:
1. Сервис или Celery-задача публикует событие в канал Redis (`realtime.publish`).
2. В каждом веб-воркере FastAPI работает **мост Redis→WebSocket** (`_realtime_ws_bridge` в `main.py`), который слушает канал и ретранслирует событие всем подключённым по WebSocket браузерам этого воркера. Мост важен потому, что при нескольких uvicorn-воркерах каждый держит свои WS-соединения — Redis раздаёт событие сразу во все.
3. Браузер по событию обновляет **живые счётчики непрочитанного**, зажигает **колокольчик уведомлений** и, если пользователь дал разрешение, показывает **браузерный пуш** (через `utils/browserNotifications.ts`, Web Notifications API — без сервера web-push/VAPID; уведомление рисует сам браузер по WS-событию).

Уведомления также хранятся в таблице `notifications` (создаются вебхуками новых лидов и генерацией задач) и доступны через отдельный роутер.

Важная деталь: **если Redis недоступен (например, локальная разработка без Docker), сервис «мягко деградирует»** — просто работает без realtime, а мост переподключается каждые 5 секунд, не роняя приложение.

### 5.6. Аутентификация и роли

- **JWT с двумя токенами:** короткоживущий access (15 мин) и долгоживущий refresh (30 дней). Короткий access снижает риск при утечке токена, refresh избавляет пользователя от частых перелогинов.
- Пароли хэшируются (`bcrypt`).
- **Роли:** `owner | manager | admin | marketer`. Проверка прав есть и на бэкенде (`role_required`), и на фронтенде (`denyRoles` в маршрутах). Дублирование намеренное: фронт прячет лишнее из UI для удобства, но реальную защиту обеспечивает бэкенд.

### 5.7. Каналы коммуникаций и боты для пациентов

Единая модель `Communication` хранит обращения из всех каналов (Telegram, Max, ВКонтакте, сайт, звонки Novofon/Ростелеком) в одном виде: канал, направление (входящее/исходящее), тип, содержимое, статус, приоритет. Поверх — ИИ-поля: теги, краткое содержание, рекомендованное следующее действие. Это и есть «единая лента входящих»: администратор видит всё в одном месте.

**Боты (Telegram + Max)** используют общий слой диалога `bot_flow.py` — конечный автомат с состоянием в Redis (ключ `bot:{channel}:{uid}`, TTL 30 мин) и короткой историей для контекста ИИ. Один код обслуживает оба мессенджера, а сборщик клавиатур отдаёт разметку сразу в двух форматах. Что умеет бот: запись на приём (имя → телефон → описание проблемы), ИИ-ответы на вопросы о клинике, показ бонусного баланса, напоминания. Служебные сообщения бота скрываются из общей ленты чата.

**Контекст бонусной программы для ИИ-ассистента.** При ответе на свободный вопрос пациента база знаний дополняется кратким описанием бонусной программы (`loyalty_service.get_ai_context`) и реально настроенными правилами начисления баллов (`describe_earning_rules`). Благодаря этому ассистент отвечает про баллы/реферальный код сам, а не отправляет звонить в клинику. В разделе бота «🎁 Бонусная программа» показываются баланс (с корректным русским склонением слова «балл»), правила начисления, персональный реферальный код и последние движения. Системный промпт ассистента сделан «тёплым»: мягкий тон, один уточняющий вопрос при неясном запросе, без навязывания звонка в каждом сообщении.

**ВКонтакте (`vk.py`)** подключён отдельным каналом через **Callback API** сообщества. Особенности, отражённые в коде: на событие `confirmation` вебхук возвращает строку-подтверждение **простым текстом** (не JSON), на прочие события — текст `ok`; проверяется `secret` сообщества, если он задан; исходящие сообщения самого сообщества (`from_id < 0`) игнорируются, а имя отправителя добирается через `users.get`. В текущей версии это **ручной чат**: входящее сообщение попадает в тред раздела «Коммуникации», автодиалога (`bot_flow`) для VK пока нет; ответ администратора уходит через `messages.send`. Канал помечается как «ВКонтакте».

Особенности эксплуатации, отражённые в коде:
- **Меню команд Telegram регистрируется при старте бэкенда** (`_register_telegram_commands`), чтобы новые пункты появлялись сразу после деплоя.
- **Webhook Telegram автоматически регистрируется при сохранении токена** в админке.
- Токены/секреты берутся сначала из БД (админка), затем из `.env` (см. §5.11).

### 5.8. Телефония: провайдер-нейтральный слой (Novofon / Ростелеком)

Приём и учёт «обычных» звонков клиники (входящие/исходящие, история, записи разговоров, задачи «Перезвонить») построены так, чтобы **провайдера АТС можно было менять переключателем**, не трогая остальной код.

- **Единый контракт.** `NovofonService` и `RostelecomService` реализуют один интерфейс: `handle_call_event` (нормализовать событие вебхука во внутренний dict), `make_call`, `get_recording`, `download_recording_bytes`, `get_call_history`. Фабрика `integrations_service.get_telephony_service` по настройке `telephony_provider` («novofon» по умолчанию / «rostelecom») собирает нужный сервис с кредами из админки. Роутеры и вебхуки работают с любым провайдером единообразно.
- **Внутренний канал остался `"novofon"`** (drop-in): это значение встречается по всему коду (история, дедупликация, дашборд, автолиды, фильтры фронта), поэтому провайдер определяет лишь источник событий и записей, а не идентификатор канала в БД.
- **Общий путь сохранения события** (`webhooks._store_call_event`): привязка к пациенту по телефону, дедупликация по `external_id` (несколько уведомлений одного сеанса сливаются в одну строку), создание задачи «Перезвонить» по пропущенным, realtime-событие и автолид — общие для обоих провайдеров.
- **Особенности Ростелеком «Виртуальная АТС»** (интеграционный API v7.5, `api.cloudpbx.rt.ru`): транспорт — подписанный `POST` JSON, подпись `X-Client-Sign = sha256hex(client_id + body + signing_key)` проверяется в обе стороны. События `call_events` (реагируем на `new` и `end`; финальные статус/длительность берём авторитетно из `call_info`, т.к. в событии длительности нет). История домена выгружается **асинхронно**: `domain_call_history` → `order_id` → вебхук `history_file_completed` → скачивание gzip-CSV → импорт в историю (кнопка «Синхронизировать»). Вебхук `get_number_info` отдаёт АТС имя пациента (Display Name) по номеру. Записи — одноразовая ссылка `get_record` (привязана к IP сервера).
- **SSL-нюанс Ростелекома.** API отдаёт сертификат «Russian Trusted CA» (Минцифры), которого нет в стандартном хранилище. В админке есть поле «Сертификат API ВАТС (PEM)» (кнопка «Скачать сертификат API» в ЛК) — вставленный сертификат используется как якорь доверия с флагом `VERIFY_X509_PARTIAL_CHAIN` (не требуя достраивания цепочки до российского корня). Есть аварийный тумблер «Не проверять SSL» — только для теста.

### 5.9. ИИ-обзвон: кампании (бэкенд) + Asterisk (телефония) + aicallrobot (голос)

Подсистема **исходящего голосового обзвона** состоит из трёх частей и намеренно разделена:

- **Бэкенд DentaFlow (`ai_calling_service.py`, модели `AiCallingCampaign`/`AiCallingCampaignItem`, задача `tasks/ai_calling.py`)** — бизнес-логика кампании: какие пациенты (из сегмента), в какие окна/по какому расписанию звонить, сколько одновременно, куда складывать исход. Диспетчер `tick_campaigns` запускается каждую минуту. Есть провайдер-нейтральный **тест-звонок** и удаление кампании.
- **Asterisk (`asterisk/`)** — телефония обзвона. Бэкенд через AMI (`asterisk_ami.py`) отправляет `Originate` в контекст `ai-outbound` с проброшенной переменной `CALL_ID`; звонок уходит через SIP, а аудио стримится в робота по **AudioSocket**. Конфиги PJSIP/manager генерируются из шаблонов, SIP-реквизиты `entrypoint.sh` тянет из админки бэкенда по внутреннему токену.
- **aicallrobot** — голосовой робот (ASR → GPT → TTS), ведёт сам разговор в реальном времени. Синтез речи (**TTS**) выбирается на уровне кампании: **Yandex SpeechKit** (по умолчанию) или **fish.audio** (модель S2.1 Pro по умолчанию, для снижения задержки ответа). Для fish.audio в поле `tts_voice` кампании хранится `reference_id` пользовательского голоса; провайдер — в `tts_provider`. Это самостоятельный подпроект со своей архитектурой — см. `aicallrobot/ARCHITECTURE.md`.

Почему так: телефония, голосовой ИИ и CRM-логика — три разные предметные области с разным темпом изменений и разными внешними сервисами. Разделив их, каждую можно развивать и перезапускать независимо; активный звонок при этом «держит слот» именно ИИ-воркера Celery, не мешая остальным задачам.

### 5.10. Бонусная программа и мотивация персонала

- **Бонусы пациентам (`loyalty_service.py`).** Настройки хранятся JSON-блобом в `integration_settings` (ключ `loyalty_config`), движения баллов — в леджере `loyalty_transactions`, а текущая сумма кэшируется в `patients.bonus_balance`. Есть реферальные коды (`patients.referral_code`), сбор и модерация отзывов (`patient_review`, скриншоты хранятся в `static/`), подарочные сертификаты/скидки.
- **Мотивация администраторов (`rewards_service.py`).** Леджер `admin_points` начисляет баллы за действия (закрытая задача, сделанный звонок, соблюдение скрипта, подтверждённый приём, «дозвон» до пациента) по настраиваемому конфигу (`rewards_config` в `integration_settings`) и строит лидерборд.

Общий приём: **редко меняющиеся настройки модулей лежат JSON-конфигом в `integration_settings`, а факты (движения баллов, отзывы) — в отдельных таблицах-леджерах.** Это даёт гибкость без миграций и полную историю операций.

### 5.11. Настройки интеграций в БД (админка), а не только в `.env`

Ключи и параметры внешних сервисов (Novofon, Ростелеком, 1Denta, Telegram, OpenAI, Max, ВКонтакте, fish.audio, почта, SIP/AMI) можно задавать **через раздел «Настройки» в интерфейсе** — они хранятся в таблице `integration_settings` и читаются сервисами в приоритете «БД → `.env`» (`integrations_service.get_raw_value`). Зачем: менять токены и проверять статус подключения без редеплоя и правки `.env` на сервере; чувствительные значения при этом не обязаны лежать в репозитории. `.env` остаётся источником значений по умолчанию и инфраструктурных параметров.

Технические детали, отражённые в коде:
- Чувствительные значения **маскируются** при отдаче на фронт (`MASKED_KEYS`, показывается `abc***xyz`); если пользователь оставил маску без изменений, при сохранении старое значение не затирается.
- У **каждого блока интеграции — своя кнопка «Сохранить»** (не одна общая на всю страницу): можно менять и проверять сервисы по отдельности.
- Помимо ключей, в `integration_settings` лежат и **редактируемые справочники/конфиги**: список источников привлечения пациентов (`patient_sources`), конфиг бонусов (`loyalty_config`), конфиг мотивации (`rewards_config`), выбор провайдера телефонии (`telephony_provider`) — их можно менять без миграций.

### 5.12. Источник привлечения пациента и аналитика по источникам

У пациента два разных «источника»:
- `source_channel` — **канал обращения** (telegram / call / site / max / referral), проставляется автоматически.
- `referral_source` — **маркетинговая атрибуция «откуда узнал о клинике»** (Рекомендации, 2ГИС, Яндекс Карты, ПроДокторов, реклама и т.д.). Это редактируемая вручную метка; список значений хранится в `integration_settings` (`patient_sources`) и правится в «Настройках» без миграций.

На этих данных строятся отчёты (`routers/reports.py`): «Источники обращений» (сколько пациентов пришло из каждого источника за период) и «Первичные пациенты» (пациенты, чей самый ранний визит попал в период, с разбивкой взрослые/дети по `birth_date` и по дням для графика) — плюс прежние отчёты по выручке, услугам и врачам. Раздел «Аналитика» доступен только ролям `owner`/`manager`.

## 6. Как это разворачивается (деплой)

Два docker-compose файла:

**Локально (`docker-compose.yml`)** — Postgres, Redis, backend (с автоперезагрузкой), celery-worker, celery-beat, фронт через `vite dev`. Всё с монтированием кода для удобной разработки.

**Прод (`docker-compose.prod.yml`)** — отличия отражают зрелость системы. Сервисы:
- `frontend` — сборка статики в volume `frontend_dist`;
- `nginx` — SSL (Let's Encrypt/`certbot`), отдаёт статику фронта и бэкенда (`/static`), проксирует `/api`;
- `backend` — стартует с `alembic upgrade head` (миграции применяются автоматически), затем uvicorn (2 воркера);
- `aicallrobot` — голосовой робот ИИ-обзвона (с данными и базой знаний в volumes);
- `asterisk` — телефония для исходящих звонков;
- `celery_worker` (`default,sync`, concurrency=4), `celery_worker_segments` (`segments`, concurrency=1), `celery_worker_ai` (`ai`) — то самое разделение очередей;
- `celery_beat` — планировщик;
- `telegram_bot` — отдельный процесс бота;
- `postgres`, `redis`.

Персистентные тома: `postgres_data`, `redis_data`, `certbot_data`, `frontend_dist`, `frontend_node_modules` (кэш для быстрых пересборок), `aicallrobot_data`, `aicallrobot_kb`, `aicall_recordings` (общий с Asterisk том с записями звонков), `backend_static` (загруженные файлы: аватары, скриншоты отзывов).

Скрипты `deploy.sh` / `update.sh` автоматизируют выкладку. Конфигурация через `.env` (`.env.example` — шаблон со всеми ключами: 1Denta, Novofon, Ростелеком (ВАТС), Telegram, OpenAI, Max, ВКонтакте (Callback API), fish.audio, почта, Asterisk/AMI, aicallrobot, внутренний сервис-токен) плюс переопределения из админки (§5.11).

## 7. Сводка по принятым решениям (кратко «почему так»)

| Решение | Причина |
|---------|---------|
| Надстройка над 1Denta, а не замена | Клиника уже работает в МИС; дешевле и безопаснее добавить слой, чем мигрировать. |
| Async везде (FastAPI, SQLAlchemy, httpx) | Много обращений к внешним API — асинхронность не блокирует процесс на ожидании сети. |
| Один часовой синк вместо частых | Частые входы на ~8 процессах упирались в троттлинг авторизации 1Denta (HTTP 423). |
| Celery + несколько очередей/воркеров | Тяжёлые задачи не мешают ни вебу, ни друг другу (синк vs сегменты vs звонки). |
| JSONB для сырых данных, ИИ-результатов и конфигов | Гибкость: новые поля/настройки без миграций, кэш ИИ и настройки модулей прямо в записи. |
| Fingerprint-кэш для ИИ | Экономия денег и времени на 17k пациентов — не анализировать неизменившихся. |
| Дешёвая модель для массового анализа | Баланс цена/качество: gpt-4o-mini для объёма, gpt-4o для точечных задач. |
| Моки в ИИ-сервисе | Разработка и демо без ключа и расходов. |
| Мягкая деградация Redis + переподключение моста | Низкий порог входа для локальной разработки, устойчивость realtime к сбоям. |
| Двойная проверка ролей (фронт+бэк) | Удобство UI + реальная безопасность на сервере. |
| Расписание задач под часовой пояс клиники | Задачи на обзвон готовы ровно к открытию клиники в Улан-Удэ. |
| Слоистость (router → service → model) | Переиспользование логики (роутер/задача/бот), тестируемость, простые роутеры. |
| ИИ-обзвон вынесен в отдельный сервис + Asterisk | Голос, телефония и CRM — разные домены; независимая разработка и перезапуск. |
| Провайдер-нейтральный слой телефонии (Novofon/Ростелеком) | Единый контракт сервисов + фабрика по настройке → смена АТС переключателем, без правок роутеров. |
| Внутренний канал телефонии оставлен `"novofon"` | Drop-in: значение зашито по всему коду (история, дедуп, автолиды, фильтры) — провайдер меняет лишь источник данных. |
| Выбор TTS-провайдера на уровне кампании (Yandex/fish.audio) | Баланс «русская речь vs задержка ответа» без жёсткой привязки всего обзвона к одному синтезу. |
| ВКонтакте как отдельный канал (Callback API, ручной чат) | Специфика VK (текстовый хендшейк confirmation, секрет, from_id<0) отделена от общего `bot_flow`. |
| `referral_source` отдельно от `source_channel` | Маркетинговая атрибуция «откуда узнал» ≠ технический канал обращения; редактируемый список без миграций. |
| Общий `bot_flow` для Telegram и Max | Один код диалога на два мессенджера, состояние в Redis с TTL. |
| Настройки интеграций в БД (админка) | Смена токенов и проверка подключений без редеплоя. |
| Отдельный процесс `telegram_bot` | Бот не зависит от перезапусков веб-воркеров. |

## 8. С чего начать изучение кода

1. `backend/app/main.py` — какие разделы API есть, мост Redis→WS, старт бота.
2. `backend/app/config.py` и `.env.example` — какие внешние сервисы подключены.
3. `backend/app/tasks/celery_app.py` — что и когда происходит в фоне (карта «жизни» системы и разделение очередей).
4. `backend/app/services/one_denta.py` — как устроен главный источник данных.
5. `backend/app/services/segments_service.py` + `tasks/segments.py` — сложный модуль (ИИ + кэш + очереди).
6. `backend/app/services/ai_calling_service.py` + `asterisk_ami.py` + `aicallrobot/ARCHITECTURE.md` — подсистема ИИ-обзвона.
7. `backend/app/services/integrations_service.py` — настройки в БД + фабрика провайдера телефонии (`get_telephony_service`); `novofon.py` / `rostelecom.py` — реализации единого контракта.
8. `backend/app/routers/webhooks.py` — приём всех входящих каналов (Telegram, Max, VK, Novofon, Ростелеком) и общий путь сохранения звонка.
9. `backend/app/services/bot_flow.py` — общая логика ботов Telegram/Max.
10. `backend/app/services/loyalty_service.py` / `rewards_service.py` — бонусы и мотивация.
11. `frontend/src/App.tsx` — карта всех страниц и прав доступа.
